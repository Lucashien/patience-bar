# 文件協作規則

## 原則

- 文件用繁體中文；程式碼、識別碼、指令保留原文。重點先行、短句、每點一件事。
- 程式碼是唯一主檔。文件只寫「是什麼、為什麼、驗證到哪」，**不複製程式碼**；需要時指向檔案路徑。
- 連結一律用 Obsidian wikilink，例如 `[[耐心條]]`，檔名不重複所以不寫路徑；要換顯示字用 `[[檔名|顯示字]]`。
- 功能頁放 `features/`，約 5 頁，一頁講「是什麼、規則、程式位置」，**不寫驗證狀態**。
- **驗證狀態只寫在 `tests/`**（測試總覽、各測試頁、手動驗證清單）。功能頁只在最後一行連到測試。
- 測試頁開頭用 frontmatter 標 `檔案`、`數量`、`最後結果`。

## 功能狀態要分清楚

每項功能分開標：

- **實作**：程式裡有。
- **驗證**：實際跑過，寫日期與環境（實機／模擬器／單元測試／電腦呼叫 API）。
- **未驗證**：寫了但沒測。

編譯成功不等於功能可用。被移除的功能保留紀錄，寫明誰決定、何時、為什麼。

## 安全

- **不寫入**：`GoogleService-Info.plist` 內容、API key、邀請碼實例、帳號密碼。
- 只寫格式與規則，不寫實例。
- 私人連結（例如設計稿）要註明「僅本人可開」。

## 改動後怎麼更新

1. 改了功能 → 更新對應的 `features/` 頁。實測了 → 只更新 `tests/`，不動功能頁。
2. 新增或改了測試 → 更新 `tests/` 對應頁與 [[測試總覽]]（數量、最後結果、缺口）。
3. 新增功能 → 優先寫進既有的功能頁；真的是新類別才開新頁，並加進 [[功能總覽]]。
4. 做了取捨或使用者改變決定 → 在 [[設計決策]] 加一列。
5. 發現問題或有新想法 → 寫進 [[待辦]]。
6. 踩到坑 → 寫進 [[開發備忘]]。
7. 在 [[log]] 最上面加一行。
8. 對照 `git log` 寫 commit 或分支；未 commit 的改動明說。
